## 1 · Ground rules

- **Never edit a generated `.svg` by hand.** Edit the spec or the emitter, then
  regenerate. `assets/examples/*.svg` are all generated and byte-reproducible.

- **One commit per concern.** Conventional prefix: `feat:`, `fix:`, `docs:`,
  `refactor:`, `test:`, `chore:`. A `refactor` that changes generated bytes is
  not a refactor.
- **Do not publish anything new, do not make the repo private, do not add
  dependencies** without asking. Python 3.9+ with stdlib is the floor; Playwright
  and Pillow are optional extras (frame rendering only).

### A · Wire the gallery tiles into the README — **do this first**

**The problem.** `scripts/build_thumbs.py` builds 12 uniform 480×360 tiles in
`docs/thumbs/`. They are committed. **The README does not use them.** It still
has the old layout:

```html
<a href="docs/gallery/README.md">
  <img src="docs/gallery/network-services.svg" ... width="24%">
```

That is why the gallery looks sparse with white gaps: the examples range from
aspect 0.97 (`network-services`) to 3.08 (`timeline-roadmap`), and four
`width="24%"` tags in a row only align when every image has the same aspect
ratio. The wide ones shrink to a slivers while the square ones tower.

**The fix.** Replace the three `<a>` blocks with a markdown table using the
tiles. `build_thumbs.py` prints the exact table when it runs:

```bash
python scripts/build_thumbs.py          # prints the suggested 3-column table
```

It prints a 3-column table (4 rows for 12 tiles; the last row may be short).
Each cell links to the full-size example:

```html
<a href="docs/gallery/network-services.svg"><img src="docs/thumbs/network-services.svg" alt="network — pulses spread by graph depth" width="100%"></a>
```

Keep the link to `docs/gallery/README.md` for the full-size annotated gallery.

**Definition of done:** the README contains a table, no `width="24%"` remains
in the gallery section, every image path in the README resolves to a tracked

### B · Document the visual grammar — accepted from PR #4

PR #4 identified that the generator's node shape, emphasis and traveller are
**choices, not accidents**, and nothing in the docs says so. The maintainer
accepted the cheap option: **document it, don't make it configurable.**

Write a section in `references/diagrams.md` (read it first for voice and
structure) covering:

- **Node shape** — one shape only: rounded `rect` with `rx=12`, emitted by
  `node_card()` in `scripts/diagram_common.py`. Why: one rail-geometry
  contract, so "motion follows drawn lines" stays checkable.
- **Emphasis** — one mechanism: a stroke overlay + `feGaussianBlur`, from
  `glow_overlay()`.
- **Traveller** — one form: a blurred halo plus a solid core, from

- **Why it is not configurable** — a node-shape parameter propagates into rail
  endpoints and tangency, which is exactly what the linter exists to police.
  Every dimension multiplies the combinations a contributor must reason about,
  and getting one wrong produces a silently wrong graphic, not an error.

### C · Add CI — the repo has none

This is the highest-value thing you can add, because every gate in this repo is
currently only run by hand.

Add `.github/workflows/ci.yml` running on push and pull_request:

```yaml
- uses: actions/checkout@v4
- uses: actions/setup-python@v5
  with: { python-version: '3.11' }
- run: python -m py_compile scripts/*.py
- run: python scripts/lint_svg_anim.py assets/examples/*.svg docs/*.svg docs/thumbs/*.svg
- run: python scripts/gen_diagram.py assets/specs/network-services.json /tmp/n.svg
      && diff /tmp/n.svg assets/examples/network-services.svg
```

The last step is the important one: **regeneration must be byte-identical**, or
a committed example has drifted from its spec.

**Line-ending trap:** `.gitattributes` pins `* text=auto eol=lf`, so on Linux CI
the `diff` above is exact. On Windows a checkout may still carry CRLF in the
working tree while the generator writes LF, and a bare `diff` then reports a
spurious difference. If you run this comparison locally and it "fails", re-run
it as `diff --strip-trailing-cr /tmp/n.svg assets/examples/network-services.svg`
before concluding anything is broken. Confirm which case you are in and say so
in your report.

**Do not** add a Playwright/Chromium step. Frame rendering needs a browser and
would make CI flaky; it is a local tool by design.

**Definition of done:** the workflow file is valid YAML, every command in it is
one you have run locally and pasted real output from, and you state plainly
that you could not execute the workflow itself — CI only proves itself on push.

## 3 · Known open items — yours to decide, not to guess at

**1 · A static-first lint check.** I attempted one and **reverted it.** The
logic: "an element hidden at t=0" is true of almost every type, because most
animate *from* zero. Telling that apart from a genuinely empty canvas needs real
layout, not XML inspection. My attempt produced **47 false positives across 68
files**. A naive reimplementation will do the same.

If you attempt it, the tractable version is **not** XML analysis — it is a
headless-Chromium check that measures painted pixels at frame 0.
`scripts/render_frames.py` already loads an SVG, calls `pauseAnimations()` and
`setCurrentTime(0)`, and screenshots; a solid-colour pixel histogram at that
point is the measurement. Keep it out of CI (§2C) for the flakiness reason.
**If you decide not to build it, that is a perfectly good outcome** — say so
explicitly rather than shipping something that cries wolf.

of history. **Do not sync it, mirror it, or delete it without asking Takim.**
Report it as an observation and let him decide. The GitHub repo is the source of
truth.
