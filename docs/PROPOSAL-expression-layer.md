# Proposal — an expression layer: node shapes, emphasis, travellers

**This PR changes no code.** It is a design proposal with a worked reference implementation sketch, so the shape of the work can be agreed before anything lands. If you disagree with the direction, closing this costs nothing.

## The observation

Every diagram the generator emits uses one visual language:

| Element | Always | Where |
|---|---|---|
| Node shape | rounded `rect`, `rx=12` | `node_card()` in `diagram_common.py` |
| Emphasis | `filter:url(#glow)` stroke overlay + `feGaussianBlur` | `glow_overlay()` |
| Traveller | a filled `circle` pair — a blurred halo `r=11` plus a solid core `r=4.6` | `relay_traveller()` |

That consistency is a genuine strength and I do not want to lose it. It is also *undiscoverable*: nothing in the docs says these are choices rather than the only option, so a reader cannot tell whether the grammar is a system or an accident of implementation.

## The proposal

Three orthogonal spec fields. Same geometry engine, same timing derivation, same palette discipline, same one-clock rule.

```jsonc
{
  "shape":     "rect",     // rect | pill | circle | hex | shield
  "emphasis":  "glow",     // glow | outline | fill | dim-others
  "traveller": "dot"       // dot | packet | pulse | comet
}
```

Defaults reproduce today's output exactly, so all 49 examples stay valid byte-for-byte. That is a hard requirement, not a hope — `CONTRIBUTING.md` says a refactor that changes generated bytes is not a refactor.

### Why orthogonally, and not more types

The tempting version is to add eight new generator types: `hexflow`, `glowless-cycle`, `packet-radial`. That is the mistake to avoid. It multiplies the space a contributor must verify, and `CONTRIBUTING.md` exists precisely because *"AI-generated SVG animation is confidently wrong."* Every new type is another emitter whose timing nobody has checked.

Three fields instead means: one shape function, one emphasis function, one traveller function. The combinatorial surface looks larger but the *code* surface is flat, and the linter's job stays tractable because the invariants (one clock, static-first, motion on rails, keyTimes end at 1) are enforced in one place rather than N.

### Why these specific values

**`emphasis: "dim-others"` is the one I would ship first.** Almost every diagram in the wild has a glow problem — when several nodes light up, or a glow so strong it blows out the fill. `dim-others` solves that by *attenuating everything that is not the active node*, which needs no new geometry at all. It is also the only value that improves an existing diagram without changing its composition.

**`shape` is the weakest of the three, and I think it should be last.** A `hex` node that is not visually load-bearing is decoration. The honest test for each shape: *does it encode something?* `circle` for a terminal/endpoint, yes. `pill` for a state chip, yes. `hex` for nothing, no. I would ship `pill` and `circle` and drop the rest.

**`traveller` is the one with the best ratio of novelty to risk.** A `packet` (small rounded square) reads as data movement where a circle reads as generic motion; a `comet` (a dot with a tapering tail) makes direction legible at a glance and needs no arrowhead. Both are the same `animateMotion` with different geometry, so the timing code is untouched.

### Cost per value

Roughly, in order of value for effort:

| Value | Effort | Risk | My recommendation |
|---|---|---|---|
| `emphasis: dim-others` | ~25 lines in `glow_overlay()` | low — pure opacity | **first** |
| `traveller: packet` | ~15 lines | low — same timing | **second** |
| `traveller: comet` | ~25 lines | low | third |
| `shape: pill` | ~30 lines | medium — changes rail endpoints | fourth |
| `shape: circle` | ~40 lines | medium — rails must become tangent | fifth |
| `emphasis: fill` | ~20 lines | medium — needs palette work | maybe not |
| `shape: hex`, `shield` | ~30 lines each | medium | **probably not** |

`shape` is the expensive one because node shapes carry consequences: a `circle` node cannot keep the current rectangular rail endpoints, so every rail in every diagram type has to learn tangency. That is the part that could quietly break the "motion follows drawn lines" rule, and it is why I would not start there.

## What I would *not* do

- **A `compose` type per combination.** That is the multiplicative path again.
- **Per-node `shape` arrays** (`shapes: ["rect","pill",…]`). Tempting, but it makes every diagram a design decision the author has to get right, and it is the fastest route to a file that is technically valid and visually incoherent.
- **A new theme.** Seven themes is plenty; a theme is a palette, not an emphasis model. `emphasis` should compose with the existing palette.

## Verification bar

Per `CONTRIBUTING.md`, each of these needs, before it lands:

1. `py_compile` clean
2. All 49 existing examples lint `0 error(s), 0 warning(s)` **and diff byte-for-byte** — this is the regression gate that proves defaults are untouched
3. A new spec + example per value, in the repo's `<type>-<topic>` naming
4. Frames inspected at 0, an arrival moment, and ~95%, described in the PR
5. The linter check from #2 run against the new example — a label inside a `circle` node is exactly the case it now catches, so it doubles as the acceptance test for `shape: circle`

Point 5 is the nice part: the check landed in #2 partly by accident, and it happens to be exactly the acceptance criterion the riskiest value needs.

## Open questions for the maintainer

1. **Is `dim-others` a per-diagram mode or per-node?** Per-diagram is simpler and I think right; per-node would let you emphasise two nodes at once.
2. **Should `shape` be restricted to specific diagram types?** A `circle` node inside a `sequence` lifeline makes no sense. Restricting it would be a smaller, safer win than making every emitter handle it.
3. **Does any of this earn its keep?** A fair answer is "no, ship `dim-others` and stop". I think that is a defensible outcome — the current single-language system is coherent, and the strongest argument for the layer is legibility of the grammar, not capability.

## What I need from you

Not a merge decision — a direction:

- **Accept the framing** and I will open small PRs in the order above, one field per PR.
- **Narrow it** — tell me which single value is worth it and I will build only that.
- **Reject it** and I will leave the system as it is. It is not broken; this is an enrichment, not a fix.

I would also accept "the grammar should just be documented, not made configurable" as an answer — a paragraph in `references/diagrams.md` saying *these are the only node shapes and traveller forms, here is why* would cost ten lines and remove most of the confusion I set out to fix.
